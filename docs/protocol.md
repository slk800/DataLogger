# DataLogger 串口协议 v1

> 面向 PC 工具 `tools/dltool.py` 的设备侧导出协议。
> 物理层：USART1，115200 8N1，无流控。

---

## 1. 设计目标

1. **可恢复**：任何字节错误都不能导致上位机卡死，最坏情况是丢一帧。
2. **可续传**：大批量导出中断后，能从指定偏移继续，不重复、不丢段。
3. **可验证**：设备端文件级 CRC 与 PC 端重算结果必须一致，导出才算成功。
4. **易调试**：纯文本命令（`help` / `status`）与二进制协议共存，不需要专用工具也能排查。

---

## 2. 帧格式

```text
+--------+----------+--------+--------+---------+---------+--------+-----+
| 0x00   | payload                                          | 0x00   |
+--------+----------+--------+--------+---------+---------+--------+-----+
          | ver | type | seq_lo | seq_hi | len_lo | len_hi | data... |
```

- 帧定界：**COBS**（Consistent Overhead Byte Stuffing）编码，帧尾追加 `0x00` 作为定界符。
  COBS 保证编码后的数据中不出现 `0x00`，因此接收端只要按 `0x00` 切分即可恢复帧。
- 帧内**不含 CRC 字节**，CRC16 放在 payload 末尾（见下）。

### 2.1 Payload 布局（解码 COBS 之后）

| 偏移 | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| 0 | 1 | `ver` | 协议版本，当前 `0x01` |
| 1 | 1 | `type` | 帧类型，见 §3 |
| 2 | 2 | `seq` | 序号，小端，请求/响应配对 |
| 4 | 2 | `len` | `data` 字节数，小端，≤ 256 |
| 6 | len | `data` | 命令参数或返回数据 |
| 6+len | 2 | `crc16` | CRC-16/CCITT-FALSE，覆盖 `ver` 到 `data` 末尾 |

CRC-16/CCITT-FALSE 参数：

```text
poly   = 0x1021
init   = 0xFFFF
xorout = 0x0000
refin  = false
refout = false
```

校验方法（Python 参考）：

```python
def crc16_ccitt(data: bytes) -> int:
    crc = 0xFFFF
    for b in data:
        crc ^= b << 8
        for _ in range(8):
            crc = ((crc << 1) ^ 0x1021) & 0xFFFF if crc & 0x8000 else (crc << 1) & 0xFFFF
    return crc
```

### 2.2 为什么用 COBS 而不是自定义帧头

- `0x00` 定界天然抗“帧头出现在数据里”的问题，不需要字节转义状态机。
- 编解码是纯函数，可以在 PC 上做穷举测试。
- 最坏情况开销是 `ceil(len/254)` 字节，对 256 字节负载几乎无感。

## 3. 帧类型

| 值 | 方向 | 名称 | 说明 |
|---:|---|---|---|
| `0x01` | PC→设备 | `HELLO` | 握手，返回固件版本与能力位 |
| `0x02` | PC→设备 | `LS` | 列出文件 |
| `0x03` | PC→设备 | `STAT` | 文件系统与运行时状态 |
| `0x04` | PC→设备 | `READ` | 按偏移读取文件 |
| `0x05` | PC→设备 | `CRC` | 取文件级 CRC 与大小 |
| `0x06` | PC→设备 | `EVENTS` | 读取事件/报警记录 |
| `0x07` | PC→设备 | `GET_CFG` | 读取配置项 |
| `0x08` | PC→设备 | `SET_CFG` | 修改配置项（仅内存） |
| `0x09` | PC→设备 | `SAVE_CFG` | 提交配置到 A/B 区 |
| `0x0A` | PC→设备 | `ERASE` | 擦除全部数据（需确认字） |
| `0x0B` | PC→设备 | `SET_TIME` | 设置墙钟（写 PCF8563） |
| `0x0C` | PC→设备 | `GET_TIME` | 读取墙钟、MKT、报警状态 |
| `0x80` | 设备→PC | `ACK` | 命令成功，`data` 为返回内容 |
| `0x81` | 设备→PC | `NAK` | 命令失败，`data[0]` 为错误码 |

- 响应帧的 `seq` 必须与请求相同。
- 设备端一次只处理一帧；PC 采用停等（stop-and-wait）策略。

### 3.1 错误码

| 值 | 名称 | 说明 |
|---:|---|---|
| `0x00` | `OK` | 成功（一般不单独使用，成功走 ACK） |
| `0x01` | `BAD_CRC` | 帧 CRC 错误 |
| `0x02` | `BAD_LEN` | 长度或参数越界 |
| `0x03` | `NO_FILE` | 文件不存在 |
| `0x04` | `NO_SPACE` | 存储空间不足 |
| `0x05` | `FLASH` | Flash 操作失败 |
| `0x06` | `UNSUPPORTED` | 未知帧类型或命令 |
| `0x07` | `BUSY` | 设备忙（Flash 锁超时） |
| `0x08` | `DENIED` | 需要确认字但未提供 |

## 4. 各命令的 data 布局

### 4.1 `HELLO`

请求 `data`：空

响应 `data`：

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 4 | 固件版本，`major.minor.patch` 各 1 字节 + 保留 1 字节 |
| 4 | 1 | 协议版本（`0x01`） |
| 5 | 1 | 能力位：bit0 文件系统（当前固定） |
| 6 | 2 | 最大单帧 data 长度（小端，256） |

### 4.2 `LS`

请求 `data`：空

响应 `data`：连续 N 条 **24 字节**记录

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 16 | 文件名，`\0` 补齐 |
| 16 | 1 | 文件类型（0=LOG, 1=CONFIG, 2=DATA, 3=EVENTS） |
| 17 | 3 | 保留 |
| 20 | 4 | 文件大小（字节，小端） |

单帧最多放 `256 / 24 = 10` 条。当前设备只有 3~4 个文件，一次 `LS` 足够；
超过 10 个文件时需要分页（未实现）。

### 4.3 `STAT`

响应 `data`：

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 4 | 已用字节 |
| 4 | 4 | 总容量字节 |
| 8 | 1 | 文件数 |
| 9 | 1 | 上次故障码 |
| 10 | 4 | 日志丢弃计数（小端，32 位） |
| 14 | 1 | 启动次数（低 8 位） |
| 15 | 1 | 保留 |

### 4.4 `READ`

请求 `data`：

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 16 | 文件名 |
| 16 | 4 | 偏移（小端） |
| 20 | 2 | 请求长度（小端，1..256） |

响应 `data`：原始文件字节，长度可能小于请求值（到文件末尾时）。
若偏移 ≥ 文件大小，返回 `NAK` + `BAD_LEN`。

### 4.5 `CRC`

请求 `data`：16 字节文件名

响应 `data`：

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 4 | 文件大小 |
| 4 | 4 | 设备端文件级 CRC32 |

PC 端导完后重算 CRC32 与之比对，不一致即判定导出失败。

### 4.6 `GET_CFG` / `SET_CFG` / `SAVE_CFG`

`GET_CFG` 请求：4 字节 key id

| id | key |
|---:|---|
| 1 | `sample_ms` |
| 2 | `log_level` |
| 3 | `name` |
| 4 | `t_low`（0.01 °C） |
| 5 | `t_high` |
| 6 | `t_hyst` |
| 7 | `t_dur`（秒） |

响应：原值（ASCII，不含 `\0`）。

`SET_CFG` 请求：

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 1 | key id |
| 1 | N | 值（ASCII） |

`SAVE_CFG` 请求：空；响应：空 ACK。

### 4.7 `SET_TIME` / `GET_TIME` / `EVENTS`

`SET_TIME` 请求：4 字节 UTC 秒（小端）。设备写入 PCF8563 后返回空 ACK。

`GET_TIME` 响应：

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 4 | 当前 UTC 秒（0 = 时钟未设置） |
| 4 | 2 | MKT，摄氏度 ×100（有符号） |
| 6 | 1 | 报警是否激活 |
| 7 | 1 | 时钟未设置标志 |

`EVENTS` 响应：

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 4 | events 文件字节数 |
| 4 | 4 | 本次上电以来产生的事件数 |

事件文件记录布局（15 字节）：

```text
kind(1) start_utc(4) end_utc(4) min_x100(2) max_x100(2) crc16(2)
```

`kind`：`1` = 高温，`2` = 低温。

### 4.8 `ERASE`

请求 `data`：4 字节魔术字 `"ERAS"`（`0x45 0x52 0x41 0x53`）。
缺失或错误 → `NAK` + `DENIED`。

## 5. 传输时序

```text
PC                                  设备
 |  ---- FRAME(seq=1, HELLO) ------->  |
 |  <--- FRAME(seq=1, ACK) ---------   |
 |  ---- FRAME(seq=2, READ..) ------>  |
 |  <--- FRAME(seq=2, ACK,data) ----   |   (超时 500ms 重发，最多 3 次)
 |  ...
 |  ---- FRAME(seq=N, CRC) --------->  |
 |  <--- FRAME(seq=N, ACK,size,crc) -   |
```

- 重发时 `seq` 不变，设备端**不缓存**上次响应，PC 需保证幂等命令（全部命令均为幂等，`ERASE` 除外——但 `ERASE` 重复执行结果相同）。
- 串口空闲 2 秒后，PC 可发送新 `HELLO` 重新同步。
- PC 侧重传上限 8 次；60% 随机丢帧下仍能完成导出（见 `tests/e2e_test.py`）。

---

## 6. 导出流程（PC 端）

```text
1. HELLO        -> 校验协议版本
2. LS           -> 找到 sample 文件
3. CRC(sample)  -> 记录设备端 size 与 crc
4. 循环 READ(offset += 256) 直到 size
5. 本地重算 CRC32，与步骤 3 比对
6. 写 CSV：ts_utc, temperature_c, adc_raw, ...
```

断点续传：把已成功写入的 `offset` 持久化到 `.dltool.state`，重连后从该偏移继续，并在结束时对**完整文件**重算 CRC 校验（而不是只校验新区段）。

---

## 7. 与现有 CLI 的关系

- 文本 CLI（`help` / `cat` / `status`）继续保留，用于人工调试。
- 二进制协议在**同一串口**上工作：Task_Proto 解析 COBS 帧，同时把可打印字符
  攒成行交给 CLI。Task_Shell 与 Task_Proto 共用接收环形缓冲区，因此二者互斥
  （同时打开会争抢字节）。
- `APP_ENABLE_PROTO` 默认 **1**；`APP_ENABLE_UART_CLI` 保持 0。
