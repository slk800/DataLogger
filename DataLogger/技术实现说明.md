# DataLogger 技术实现说明

> 适用工程：STM32F103C8T6 + FreeRTOS + SSD1306 + W25Q64 + NTC  
> 文档日期：2026-06-11  
> 本文面向固件开发、维护、代码评审和项目答辩。

## 1. 实现目标

DataLogger 的技术目标不是简单地把若干外设驱动拼接在一起，而是建立一条可以验证的数据链：

```text
真实模拟量输入
  -> 稳定采样与物理量换算
  -> 多任务环境下的数据发布
  -> 本地可操作的人机界面
  -> 带 CRC 的持久化记录
  -> 异常复位后的有效数据恢复
```

实现需要同时满足以下约束：

- MCU 只有 20 KB SRAM，必须控制任务栈、堆和全局缓冲区。
- OLED、Flash 和 NTC 采样具有不同的时间特性，不能全部塞入一个阻塞式主循环。
- W25Q64 页编程只能将位从 1 写为 0，重新写入前必须按扇区擦除。
- Flash 写入不是原子操作，复位可能发生在数据写入和元数据提交之间。
- OLED 是主界面，系统在不连接串口模块时仍应完整工作。
- 调试故障处理不能依赖可能已经损坏的任务栈或 RTOS 同步对象。

## 2. 分层架构

工程按硬件、基础服务、业务逻辑和交互层组织：

```text
+------------------------------------------------------+
| App: 启动、DataProd、Logger、Display、Shell、Monitor |
+------------------------------------------------------+
| UI / Log / Config / FS / Sensor                      |
+------------------------------------------------------+
| BSP: Flash、SPI、UART、OLED I2C、Key                 |
+------------------------------------------------------+
| STM32 HAL / FreeRTOS / CMSIS                         |
+------------------------------------------------------+
| STM32F103 + NTC + SSD1306 + W25Q64                   |
+------------------------------------------------------+
```

### 2.1 Core 和 HAL 层

`Core/` 由 STM32CubeMX 生成并进行必要修改，负责：

- 系统时钟树。
- GPIO 复用和上下拉。
- ADC1、I2C1、SPI1、USART1 初始化。
- HAL 时基和中断入口。
- FreeRTOS 配置文件。

该层不实现业务语义。例如 ADC 层只知道读取通道 0，不知道该电压代表温度。

### 2.2 BSP 层

`BSP/` 将 HAL 外设封装成板级能力：

- `bsp_spi.c`：SPI1 字节/缓冲区传输和 W25Q64 片选。
- `bsp_flash.c`：JEDEC ID、读、页编程、擦除和 Flash 互斥锁。
- `bsp_oled_i2c.c`：SSD1306 设备就绪检查和 I2C 发送。
- `bsp_key.c`：三键扫描、消抖、短按和长按事件。
- `bsp_uart.c`：可选调试输出及 UART 互斥保护。

BSP 不关心文件名、页面或日志等级，只向上提供硬件操作接口。

### 2.3 服务层

| 模块 | 责任 |
| --- | --- |
| `Sensor/` | ADC 样本处理、NTC 电阻和温度换算 |
| `FS/` | W25Q64 地址空间、超级块、索引和文件操作 |
| `Log/` | 文本日志队列、结构化样本和启动恢复 |
| `Config/` | A/B 双区配置加载、保存和修复 |
| `UI/` | 页面状态机、显示快照和页面渲染 |
| `OLED/` | SSD1306 帧缓冲、字符绘制和整屏刷新 |

### 2.4 应用任务层

`App/` 决定各服务如何协作：

- `Task_DataProducer` 周期采样并提交数据。
- `Task_Logger` 异步持久化文本日志。
- `Task_Display` 扫描按键、执行动作并刷新 OLED。
- `App_Init` 建立服务、IPC 对象和任务。

## 3. 启动和控制流

### 3.1 MCU 启动

复位后，启动文件设置主栈、初始化 `.data/.bss`，随后进入 `main()`：

```c
HAL_Init();
SystemClock_Config();
MX_GPIO_Init();
MX_ADC1_Init();
MX_SPI1_Init();
MX_I2C1_Init();
MX_USART1_UART_Init();
App_Init();
```

`App_Init()` 内部完成应用服务初始化和调度器启动。调用 `vTaskStartScheduler()` 后，控制权不应再返回 `main()`。

### 3.2 应用初始化顺序

初始化顺序具有依赖关系：

```text
UART
  -> W25Q64/BSP Flash
  -> 文件系统
  -> 日志文件与样本恢复
  -> EventGroup
  -> 配置加载
  -> ADC 校准/NTC 初始化
  -> UI 状态初始化
  -> 创建任务
  -> 启动调度器
```

关键依赖：

- 文件系统依赖 W25Q64 已通过 JEDEC ID 检查。
- 日志初始化依赖文件索引缓存已加载。
- 配置保存依赖 Flash 互斥锁已经创建。
- UI 状态初始化依赖配置已加载，否则首页设备名和采样周期不正确。
- DataProd 启动后会扫描样本数量，因此日志恢复必须在任务创建前完成。

### 3.3 初始化失败策略

- W25Q64 初始化失败：停机，避免在未知存储状态下继续运行。
- 文件系统检测为未格式化：执行格式化后重新初始化。
- 配置 A/B 区均无效：加载默认配置并尝试保存。
- OLED 初始化失败：系统任务继续运行，Display 周期尝试恢复 OLED。
- 任务创建失败：停机并保留调试现场。

## 4. 时钟和寄存器配置

### 4.1 RCC 时钟树

外部 8 MHz HSE 经 PLL x9 输出 72 MHz：

```text
HSE 8 MHz -> PLL x9 -> SYSCLK 72 MHz
                         |
                         +-> AHB 72 MHz
                         +-> APB1 36 MHz
                         +-> APB2 72 MHz
                         +-> ADC 12 MHz (APB2/6)
```

AixProbe 实测关键寄存器：

| 寄存器 | 值 | 解读 |
| --- | --- | --- |
| `RCC_CR` | `0x03035B83` | HSE、HSI、PLL 均开启且就绪 |
| `RCC_CFGR` | `0x001D840A` | PLL 为系统时钟，HSE x9，APB1/2，ADC/6 |
| `RCC_AHBENR` | `0x00000014` | 所需 AHB 时钟开启 |
| `RCC_APB2ENR` | `0x00005A3D` | GPIO、ADC1、SPI1、USART1 等开启 |
| `RCC_APB1ENR` | `0x10200000` | I2C1 和相关 APB1 外设开启 |

### 4.2 内部 Flash

`FLASH_ACR=0x32`：

- `LATENCY=2`，适配 72 MHz。
- Prefetch buffer 启用。
- Prefetch 状态就绪。

该 Flash 是 STM32 程序 Flash；日志数据存储使用外部 W25Q64，两者不要混淆。

## 5. FreeRTOS 实现

### 5.1 内核配置

| 配置 | 数值 | 含义 |
| --- | ---: | --- |
| `configUSE_PREEMPTION` | 1 | 抢占式调度 |
| `configTICK_RATE_HZ` | 1000 | 1 ms Tick |
| `configMAX_PRIORITIES` | 7 | 优先级 0 至 6 |
| `configTOTAL_HEAP_SIZE` | 7168 | heap_4 动态堆 |
| `configUSE_MUTEXES` | 1 | 启用互斥量和优先级继承 |
| `configCHECK_FOR_STACK_OVERFLOW` | 2 | 上下文切换时检查栈边界 |
| `configUSE_MALLOC_FAILED_HOOK` | 1 | 启用申请失败钩子 |
| `configUSE_TIMERS` | 0 | 不创建软件定时器任务 |
| `configUSE_16_BIT_TICKS` | 0 | 使用 32 位 Tick |

### 5.2 任务模型

| 任务 | 优先级 | 栈 | 阻塞点 |
| --- | ---: | ---: | --- |
| Logger | 3 | 256 words | `xQueueReceive()`、Flash mutex |
| DataProd | 2 | 256 words | Flash mutex、`vTaskDelay()` |
| Display | 2 | 256 words | Flash mutex、`vTaskDelay(50ms)` |
| Shell | 4 | 256 words | 默认不创建 |
| Monitor | 1 | 128 words | 默认不创建 |

Logger 优先级高于 DataProd 和 Display，是为了在队列中出现日志时尽快取走记录，降低队列满的概率。Logger 大多数时间阻塞在队列上，不会持续占用 CPU。

DataProd 与 Display 同优先级，通过阻塞和时间片自然交替。DataProd 每轮结束调用 `vTaskDelay(sample_interval_ms)`；Display 每 50 ms 延时一次。

### 5.3 RTOS 对象

| 对象 | 类型 | 用途 |
| --- | --- | --- |
| `s_LogQueue` | Queue，16 x 80 bytes | DataProd/业务代码向 Logger 传递文本日志 |
| `s_FlashMutex` | Mutex | 串行化 W25Q64 访问 |
| `s_ui_mutex` | Mutex | 保护 `UiStatus_t` 快照 |
| `s_uart_tx_mutex` | Mutex | 保护可选 UART 发送 |
| `s_SysEvents` | EventGroup | 发布文件系统就绪和控制事件 |

### 5.4 并发边界

Flash 是共享串行设备。以下操作必须持有 `s_FlashMutex`：

- DataProd 追加 `sample`。
- Logger 追加 `log`。
- Display 保存配置、清除文件系统。

UI 不直接读取 DataProd 的局部变量。生产者通过 `UI_Status_Update*()` 更新共享状态，Display 使用 `UI_Status_GetSnapshot()` 一次性复制 120 字节快照，然后在锁外完成字符串格式化和 OLED I2C 发送。这样可以缩短 UI mutex 持有时间。

## 6. NTC 采集实现

### 6.1 ADC 配置

ADC1 配置：

- 通道：`ADC_CHANNEL_0`，对应 PA0。
- 单通道、单次转换。
- 软件触发。
- 右对齐，12 位结果。
- 采样时间：71.5 ADC cycles。
- ADC 时钟：12 MHz。

长采样时间适合热敏模块这类低速信号，可降低源阻抗和走线噪声对采样保持电容充电的影响。

启动时调用 `HAL_ADCEx_Calibration_Start()` 完成 F1 ADC 校准。

### 6.2 单次读取

每个原始样本执行：

```text
HAL_ADC_Start
  -> HAL_ADC_PollForConversion(timeout=10ms)
  -> HAL_ADC_GetValue
  -> HAL_ADC_Stop
```

ADC 在采样间隔内保持停止，因此调试暂停时看到 `ADON=0` 不表示 ADC 未工作。

### 6.3 抗噪处理

一次温度读取收集 16 个原始样本：

```c
sum = sample[0] + ... + sample[15];
sum -= min;
sum -= max;
raw = sum / 14;
```

该方法对单个尖峰和单个低谷具有容错能力，计算量小，适合 Cortex-M3。

### 6.4 电气模型

模块等效结构为：

```text
3.3V -- 10K fixed --+-- AO/PA0
                    |
                  NTC 10K
                    |
                   GND
```

因此：

```text
Vout(mV) = ADC * 3300 / 4095
Rntc     = 10000 * Vout / (3300 - Vout)
```

温度使用 Beta 模型：

```text
1/T = 1/T0 + ln(R/R0)/B
```

其中：

- `T0=298.15K`。
- `R0=10000Ω`。
- `B=3950`。

### 6.5 滤波

第一次有效温度直接作为滤波输出。之后使用整数 IIR：

```text
filtered = (filtered * 7 + current) / 8
```

这相当于新值权重 `1/8`。优点是显示稳定；代价是温度变化响应会有延迟。

### 6.6 异常分类

原始 ADC 先做电气故障判断，再做温度范围判断：

- `<20`：SHORT。
- `>4075`：OPEN。
- 温度低于 -20.0°C 或高于 125.0°C：RANGE。
- HAL ADC 操作失败：ADC。

异常记录仍可写入 `sample`，其中 `ntc_status` 标记状态，便于离线分析故障发生时间。

## 7. DataProd 数据生产流程

`Task_DataProducer()` 是系统的数据主路径。每轮流程如下：

```text
读取 Tick
  -> Sensor_NTC_Read
  -> 生成 SampleRecord_t
  -> 获取 Flash mutex
  -> 追加 sample 文件
  -> 释放 Flash mutex
  -> 更新 UI 传感器状态
  -> 格式化文本 LogRecord_t
  -> 更新 UI 生产者状态
  -> 投递文本日志队列
  -> 按配置周期延时
```

只有 `Log_AppendSample()` 成功时 `s_counter` 才递增。因此 OLED 的 `Cnt` 表示成功持久化的有效样本数量，而不是传感器读取次数。

该语义可以直接暴露存储故障：如果温度在变化但计数不增长，问题位于样本验证或 Flash 写入链，而不是 ADC 链。

DataProd 同时产生两份数据：

1. 24 字节结构化样本，用于可靠保存和机器解析。
2. 80 字节文本日志，用于 OLED 摘要和人工阅读。

## 8. 文本日志实现

### 8.1 记录格式

`LogRecord_t` 固定为 80 字节：

| 字段 | 大小 | 含义 |
| --- | ---: | --- |
| `timestamp` | 4 | FreeRTOS Tick |
| `level` | 1 | DEBUG/INFO/WARN/ERROR |
| `len` | 1 | 有效文本长度 |
| `reserved` | 2 | 对齐 |
| `msg` | 68 | 文本内容 |
| `crc` | 4 | `msg[0..len)` 的 CRC32 |

### 8.2 队列解耦

生产者调用 `Log_Submit()`，最多等待 50 ms 将记录复制到队列。Logger 任务收到记录后再执行 Flash 操作。

这种设计将日志文本的生产和持久化解耦：

- 业务任务不需要等待 Logger 从队列取数据。
- Flash 短暂繁忙时可以由 16 项队列吸收抖动。
- 队列满时明确增加 `g_log_dropped`，不无限阻塞业务。

队列的数据区约占 `16 * 80 = 1280` 字节，另有 Queue 控制结构开销。

### 8.3 当前限制

文本日志使用文件级 CRC 和追加机制，但尚未像 `sample` 一样实现逐记录启动恢复。发生提交窗口中断时，文本日志可能停止追加或需要清除文件系统。这是后续可靠性优化点。

## 9. 结构化样本实现

### 9.1 数据格式

`SampleRecord_t` 固定为 24 字节：

| 偏移 | 字段 | 大小 | 含义 |
| ---: | --- | ---: | --- |
| 0 | `timestamp` | 4 | 采样 Tick |
| 4 | `sample_count` | 4 | 写入前的样本序号 |
| 8 | `temperature_x10` | 4 | 0.1°C 定点温度 |
| 12 | `adc_raw` | 2 | 12 位 ADC 平均值 |
| 14 | `voltage_mv` | 2 | AO 电压 mV |
| 16 | `ntc_status` | 1 | 传感器状态 |
| 17 | `reserved` | 3 | 预留和对齐 |
| 20 | `crc` | 4 | 前 20 字节 CRC32 |

固定大小设计便于：

- 使用 `offset = index * 24` 随机读取。
- 在启动时逐条扫描。
- 在 PC 工具中按结构直接解析。
- 检测半写记录和位翻转。

### 9.2 CRC 算法

工程使用 IEEE 802.3 CRC32，反射多项式 `0xEDB88320`：

- 初值：`0xFFFFFFFF`。
- 查表逐字节更新。
- 结果异或：`0xFFFFFFFF`。

记录 CRC 只覆盖 CRC 字段之前的 20 字节。

### 9.3 预留空间

`sample` 第一次追加时请求 2 MB，向上按 4 KB 扇区对齐。索引中的 `reserved[0..1]` 保存分配扇区数：

```text
allocated_size = sector_count * 4096
```

文件逻辑大小随记录增长，物理容量保持 2 MB。这样后续样本可以原地页安全追加，不必每条记录重新迁移整个文件。

## 10. W25Q64 驱动

### 10.1 SPI 参数

- SPI1 主机。
- 8 位全双工。
- CPOL=0、CPHA=0，即 Mode 0。
- APB2=72 MHz，预分频 8，SPI 时钟约 9 MHz。
- 软件 NSS，PB0 作为 CS。

### 10.2 初始化

`BSP_Flash_Init()` 调用 `BSP_Flash_ReadJEDECID()`：

```text
CS low -> 0x9F -> read EF 40 17 -> CS high
```

只有 ID 等于 `0xEF4017` 才创建 Flash mutex 并返回成功。

### 10.3 读写协议

读取：

```text
WaitBusy -> CS low -> 0x03 -> 24-bit address -> receive data -> CS high
```

页编程：

```text
WaitBusy -> WriteEnable(0x06) -> CS low
-> PageProgram(0x02) -> address -> data -> CS high -> WaitBusy
```

扇区擦除：

```text
address align 4KB -> WriteEnable -> 0x20 -> address -> WaitBusy
```

`FS_PageSafeWrite()` 根据当前页剩余空间切分写入，保证单次 Page Program 不跨 256 字节页边界。

### 10.4 互斥范围

底层单个 BSP 函数本身不获取 mutex，由调用链在事务外层持锁。这样一个文件追加操作可以连续完成：

```text
校验旧数据 -> 写新数据 -> 更新索引 -> 更新超级块
```

若每个底层 SPI 操作单独加锁，其他任务可能在事务中间插入，破坏文件系统的一致性假设。

## 11. 文件系统实现

### 11.1 空间布局

```text
0x000000 - 0x000FFF  SuperBlock
0x001000 - 0x003FFF  File index table
0x004000 - 0x005FFF  Config A
0x006000 - 0x007FFF  Config B
0x008000 - 0x7FFFFF  File data
```

配置区位于文件数据区之前，并由 Config 模块独立管理。

### 11.2 超级块

`SuperBlock_t` 为 24 字节：

| 字段 | 作用 |
| --- | --- |
| `magic` | `0xDEADBEEF`，识别格式 |
| `version` | 文件系统版本 |
| `file_count` | 有效文件数量 |
| `next_write_addr` | 下一数据分配位置 |
| `total_data_size` | 数据容量统计 |
| `crc` | 前 20 字节 CRC32 |

启动时验证 magic 和 CRC，成功后将超级块加载到 SRAM。

### 11.3 文件索引

索引最多 32 项，每项 32 字节，共 1024 字节并常驻 SRAM：

| 字段 | 作用 |
| --- | --- |
| `name[16]` | 文件名 |
| `start_addr` | 数据首地址 |
| `size` | 逻辑数据长度 |
| `crc` | 文件内容 CRC32 |
| `flags` | `0xAA` 有效，`0x00` 删除 |
| `type` | LOG/CONFIG/DATA |
| `reserved[2]` | sample 用于记录预留扇区数 |

索引缓存 `s_index_cache[32]` 使文件查找无需每次读取 Flash。

### 11.4 创建文件

创建流程：

1. 验证文件名。
2. 检查同名文件。
3. 查找空闲索引项。
4. 初始化空文件条目。
5. 擦除并重写索引扇区。
6. 更新文件数并刷新超级块。

### 11.5 普通追加

`FS_File_Append()` 支持：

- 校验旧文件 CRC。
- 在已有扇区容量内原地追加。
- 检查目标区仍为 `0xFF`。
- 容量不足时分配新区域并复制旧数据。
- 重新计算 CRC、提交索引和超级块。

### 11.6 预留追加

`FS_File_AppendReserved()` 专用于 `sample`：

- 首次写入一次性分配 2 MB。
- 后续只在已分配区内追加。
- 超过预留容量返回 `FS_ERR_NO_SPACE`。
- 不迁移文件，避免随着样本增长反复复制大文件。

### 11.7 分配和冲突检查

`FS_AllocDataBlock()` 以扇区为擦除边界，分配前调用 `FS_ValidateAllocRange()` 检查目标扇区是否覆盖其他有效文件。

普通 DATA 文件不允许覆盖。LOG 类型允许按现有策略跳过或回绕，但 sample 被定义为 DATA，并通过固定预留区保护，不会自动覆盖。

## 12. Flash 一致性模型

### 12.1 提交顺序

文件追加的主要顺序为：

```text
1. 验证旧文件
2. 写入新数据
3. 更新内存中的 FileEntry
4. 持久化索引
5. 持久化 SuperBlock
```

索引是文件数据是否可见的主要提交点。该顺序确保不会先声明数据存在、再去写数据。

### 12.2 复位窗口

若在步骤 2 和步骤 4 之间复位，Flash 可能出现：

```text
数据记录有效
文件 size 仍为旧值，或 CRC 尚未更新
```

若在索引扇区擦写过程中复位，索引项也可能出现部分更新。当前文件系统不是完整事务型文件系统，因此需要应用级恢复策略。

### 12.3 sample 恢复

结构化样本拥有记录级 CRC，可以绕过损坏的文件级 CRC验证真实数据：

```text
读取索引中的 size
  -> 按 24 字节逐条读取
  -> 验证记录 CRC
  -> 得到连续有效前缀 N
  -> 对 N*24 字节重算文件 CRC
  -> FS_File_RepairPrefix 提交修复后的 size/CRC
```

恢复只接受从文件开头连续有效的记录。中间出现损坏后，后续记录即使偶然 CRC 正确也不被接受，避免形成不连续时间序列。

### 12.4 配置一致性

配置采用不同策略：A/B 双副本。

```text
写 B -> 验证 B -> 写 A -> 验证 A
```

每份配置有独立 CRC 和版本号。启动时：

- A/B 均有效：选择版本号较高者。
- 仅一份有效：加载有效副本并修复另一份。
- 均无效：加载默认配置。

文件日志使用记录恢复，配置使用双副本，分别匹配其数据形态和更新频率。

## 13. OLED 驱动和 UI

### 13.1 帧缓冲

SSD1306 分辨率为 128x64，单色帧缓冲大小：

```text
128 * 64 / 8 = 1024 bytes
```

绘制函数只修改 SRAM 帧缓冲。`SSD1306_UpdateScreen()` 再将 8 个 page 发送到 OLED。

这种双阶段设计避免边绘制边通信导致画面撕裂，也让多个文本字段可以一次更新。

### 13.2 UI 状态快照

`UiStatus_t` 为 120 字节，包含：

- 运行时间和 Tick。
- 样本数、温度、ADC、电压、电阻、NTC 状态。
- 最近日志、日志丢弃数。
- Flash 容量和文件数。
- 堆状态。
- 当前配置。
- Flash、FS、OLED 状态位。

DataProd、Display 和其他模块通过更新函数写入状态；Display 获取完整副本后渲染。

### 13.3 菜单状态机

菜单状态由三个维度组成：

```text
page   = Home/System/Flash/Log/Config/Action
mode   = Browse/Edit/Confirm
cursor = Config 或 Action 中的当前项目
```

按键扫描输出语义事件，而不是直接修改 UI：

```text
GPIO -> KEY_EVENT_UP_SHORT
     -> KEY_EVENT_DOWN_SHORT
     -> KEY_EVENT_OK_SHORT
     -> KEY_EVENT_OK_LONG
```

`UI_Menu_HandleKey()` 将事件转换为：

- 页面或光标变化。
- 配置值变化。
- `SAVE_CONFIG`、`ERASE_DATA`、`REBOOT` 动作。

动作由 Display 任务执行，UI 状态机本身不直接操作 Flash 或复位 MCU，从而保持界面逻辑和硬件副作用分离。

### 13.4 刷新调度

Display 主循环周期 50 ms：

- 每轮更新系统状态和扫描按键。
- 每 2 秒更新 Flash 容量信息。
- 每 1 秒执行常规 OLED 刷新。
- 有按键事件或动作时立即刷新。
- OLED 不就绪时每 1 秒尝试恢复。

因此按键响应不受 1 秒屏幕刷新周期限制。

## 14. 内存设计

### 14.1 构建资源

最终 Keil 构建：

```text
Code    = 36578 bytes
RO-data =  2626 bytes
RW-data =   284 bytes
ZI-data = 16156 bytes
ROM     = 39488 bytes
RAM     = 16440 bytes
```

STM32F103C8T6 标称 SRAM 为 20 KB，静态 RAM 仍保留约 4 KB 地址空间余量。这里的 ZI 已包含 FreeRTOS heap 数组、OLED 缓冲、索引缓存和其他全局对象。

### 14.2 主要 RAM 消耗

| 项目 | 约占用 |
| --- | ---: |
| FreeRTOS heap | 7168 bytes |
| SSD1306 帧缓冲 | 1024 bytes |
| 文件索引缓存 | 1024 bytes |
| 文本日志队列数据 | 1280 bytes + 控制结构 |
| 三个默认任务栈 | 3 x 1024 bytes |
| UI 状态 | 120 bytes |
| FS 索引写回扇区缓冲 | 4096 bytes，静态 |

部分对象位于 FreeRTOS heap，部分位于 `.bss`，不能简单将表中数字全部相加作为链接 ZI；表用于识别主要内存热点。

### 14.3 栈设计

DataProd 使用 `snprintf`、浮点数学库、CRC、Flash 文件系统和多层函数调用，128 words 栈曾发生溢出。修正为 256 words 后，AixProbe 检测历史最小剩余约 124 words。

栈检查使用 FreeRTOS mode 2，在任务切换时检查栈边界填充值。

### 14.4 浮点实现

STM32F103 Cortex-M3 没有硬件 FPU。`logf()` 和浮点除法由软件库实现，会增加代码体积和 DataProd 调用深度。项目只在低频温度换算中使用浮点，实时性可接受。

## 15. 故障诊断设计

### 15.1 故障记录

全局故障变量：

```c
volatile uint32_t g_fault_code;
volatile uint32_t g_fault_task_handle;
volatile char     g_fault_task_name[16];
```

定义：

- `0`：无记录故障。
- `1`：FreeRTOS 栈溢出。
- `2`：FreeRTOS 动态内存申请失败。

故障钩子只写这些变量后停机，不调用 UART、printf、队列、互斥量或 Flash。

### 15.2 为什么故障钩子不能打印

故障可能发生在 PendSV、中断上下文、栈已损坏或持有 mutex 时。此时调用普通 UART 服务可能：

- 再次获取 mutex。
- 调用不允许在 ISR 使用的 FreeRTOS API。
- 使用更多已经不足的任务栈。
- 覆盖最初故障现场。

因此调试器直接读取固定 SRAM 变量更可靠。

### 15.3 Core Fault 寄存器

AixProbe 验证中读取：

- `CFSR=0`。
- `HFSR=0`。
- `MMFAR/BFAR` 无有效 Fault 状态。

说明最终固件没有 MemManage、BusFault、UsageFault 或 HardFault。

## 16. AixProbe 调试流程

推荐顺序：

1. `connect` 建立 OpenOCD 会话。
2. 读取 `DBGMCU_IDCODE` 确认 STM32F103，DEV_ID 为 `0x410`。
3. 运行目标一段时间后 `halt`。
4. 读取 Core registers：PC、LR、SP、MSP、PSP、xPSR、BASEPRI。
5. 读取 SCB Fault 寄存器。
6. 按 SVD 解码 RCC、GPIO、FLASH。
7. 检查 ADC1、I2C1 和 SPI1 状态。
8. 读取故障变量、任务 TCB、栈填充值和业务状态变量。
9. 恢复运行，避免板子停在调试暂停状态。

### 16.1 PC 解释

单次 halt 停在 Idle task、`vTaskDelay()`、队列等待或 HAL 轮询都可能是正常现象。判断“卡死”应多次运行/暂停并结合：

- PC 是否总在同一条不可退出的分支。
- xPSR 是否处于异常上下文。
- Fault 状态。
- 任务 TCB 中保存的 PC。
- 业务计数是否随时间变化。

### 16.2 外设状态判定

- I2C1 空闲：`PE=1`、`BUSY=0`、无错误位。
- SPI1 空闲：主机已启用、`TXE=1`、`BSY=0`。
- ADC 空闲：转换结束后停止属于设计行为。
- GPIOB PB12/13/14 未按时为高电平，符合内部上拉。

## 17. 烧录实现

Keil 生成 AXF 和 HEX。AixProbe 烧录流程：

1. 使用 `fromelf --bin` 从最新 AXF 导出 BIN。
2. 校验 BIN 大小和 SHA-256。
3. 通过 MCP 上传完整 Base64 数据。
4. 写入 `0x08000000`。
5. 启用写后 verify。
6. `reset run` 启动。
7. 读取运行状态确认新固件生效。

当前交付 BIN 大小为 39488 字节，校验值见 `FIRMWARE_SHA256.txt`。

## 19. 设计取舍

### 19.1 为什么 OLED 是主界面

系统可脱离 PC 和转串口模块独立运行，更符合嵌入式设备形态。串口只保留为调试通道，减少常驻任务和 RAM 占用。

### 19.2 为什么样本同步写、文本日志异步写

样本计数的语义要求“写入成功才递增”，同步写可以明确确认持久化结果。文本日志允许短暂排队或丢弃，因此使用队列异步写更合适。

### 19.3 为什么不使用动态分配每条记录

记录和消息采用固定结构，队列执行复制，避免长期运行中的堆碎片和所有权问题。

### 19.4 为什么使用自定义文件系统

项目需要展示 Flash 页/扇区、索引、CRC 和恢复机制的实现过程，自定义文件系统提供了可解释性。但若目标变为生产级长期运行，LittleFS 等成熟方案会提供更完整的掉电保护和磨损均衡。

## 20. 当前技术债务和演进方向

建议沿可靠性主线继续优化，而不是增加无关模块：

1. **文本日志记录级恢复**：为 `log` 增加逐条扫描和有效前缀修复。
2. **批量元数据提交**：样本数据连续写入，按批次更新索引和超级块，降低擦写频率。
3. **双超级块或提交日志**：提升文件系统元数据自身的掉电恢复能力。
4. **样本区环形策略**：预留区写满后按扇区覆盖最旧数据，并保存首尾序号。
5. **温度标定参数持久化**：保存实际固定电阻、Beta 和温度偏移。
6. **运行统计**：保存每个任务的最小栈余量、Flash 写失败次数和 OLED 恢复次数。
7. **主机侧解析工具**：只实现离线读取和 CSV 导出，不改变设备主架构。

这些方向都围绕“真实采集、可靠日志、可验证证据”深化，不需要引入蓝牙、云平台或复杂网络协议。
