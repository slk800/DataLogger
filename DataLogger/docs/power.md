# 功耗设计与实测

> 本文记录 DataLogger 的低功耗实现、预算模型与实测方法。
> 模型数字来自器件数据手册，**实测数字在有硬件后补入 §5**。

---

## 1. 为什么分两层看

低功耗有三个层级，任何一层不处理都会让另外两层的努力白费：

| 层级 | 内容 | 软件能否解决 |
|---|---|---|
| **板级** | 电源 LED、LDO 静态电流、模块板载器件 | ❌ 只能改硬件 |
| **器件级** | OLED 电荷泵、Flash 待机、传感器分压 | ✅ 驱动层可关 |
| **系统级** | tickless 空闲、外设门控、事件驱动刷新 | ✅ 本文重点 |

Blue Pill 的板级地板：

- 电源 LED：3.3 V 经 1 kΩ 限流，**≈ 2 mA**
- AMS1117：静态电流 **3–5 mA**

这两项合计 5–7 mA，**比整套软件优化后的目标（54 µA）高两个数量级**。
所以只有两条路：

1. 换板（Nucleo-F103RB 的 IDD 跳线）或割线（拆 LED）
2. 接受地板，把叙事改成"单条样本能耗"与"相对改善倍数"

## 2. 软件实现

### 2.1 tickless 空闲

`configUSE_TICKLESS_IDLE = 2`，由应用实现 `vPortSuppressTicksAndSleep`
（`App/task_idle_hook.c`）。port.c 只在 `== 1` 时提供该函数，所以必须自己写。

睡眠时长用 RTC 秒差测量：

```text
读 UTC → 门控器件 → 关中断 → STOP → 开中断 → 恢复器件
      → 补 tick → 重装 SysTick → yield
```

**关键约束**：`HAL_Delay` 与各 HAL 超时依赖 SysTick。关中断期间 tick 冻结，
因此所有器件门控必须在关中断**之前**完成。这条规则写在 `task_idle_hook.c`
的文件头注释里，改代码前请先读。

### 2.2 唤醒源

PCF8563 CLKOUT 1 Hz → PB1 → EXTI1。

为什么不用 RTC alarm：PCF8563 的 alarm 只有分/时/日/星期，**没有秒**，
1 秒采样档无法用它唤醒。CLKOUT 可以覆盖所有档位。

代价是每秒必醒一次。0.3 ms @ 15 mA ≈ 4.5 µA 平均，可以接受。

### 2.3 外设门控

| 器件 | 动作 | 效果 |
|---|---|---|
| OLED | `0x8D 0x10` + `0xAE` | ~8 mA → ~10 µA |
| W25Q64 | `0xB9` 深睡 | ~4 mA → ~1 µA |
| 按键 | 改为 EXTI 唤醒 | 消除 50 ms 轮询（≈1.4 mA） |
| OLED 刷新 | 事件驱动 + 空闲降频 | 1 Hz → 按需 |

按键改 EXTI 是单项收益最大的软件改动：原来每 50 ms 醒一次扫键，
占空比 4%，在 15 mA 的有源电流上就是 600 µA——比整个 60 s 档预算还高。

### 2.4 Flash 写放大

每 32 条记录提交一次（索引 + 超级块各一次扇区擦除）。
相比逐条提交，擦除次数降低 32 倍：

```text
逐条：2 次擦除/条 × 1 条/60 s = 0.033 次/s
批量：2 次擦除/批 / 32 条 × 1 条/60 s = 0.001 次/s
```

## 3. 预算模型

`tools/power_budget.py` 按器件手册值建模，W3 实测时逐项对照。

### 3.1 干净配置（拆 LED + HT7333 + 裸 NTC）

```text
$ python tools/power_budget.py --interval 60

MCU STOP 静态        20.0 µA   RM0008 Table 27
OLED 休眠            10.0 µA   0xAE + 关电荷泵
OLED 刷新             7.5 µA   60 次/小时
每周期采样            6.2 µA   25 ms / 60 s
每秒唤醒              4.5 µA   0.3 ms @ 15 mA
LDO 静态              4.0 µA   HT7333
W25Q64 深睡           1.0 µA   0xB9
Flash 擦写            0.7 µA   每 32 条提交
------------------------------------------
合计                 54.0 µA  ≈ 772 天（1000 mAh）
```

### 3.2 原版 Blue Pill

```text
$ python tools/power_budget.py --interval 60 --board-led --no-ldo-swap --sensor-module

LDO 静态           4000.0 µA   AMS1117
板载电源 LED       2000.0 µA   软件无法关闭
NTC 模块常驻       1000.0 µA   LM393 + LED
...（软件项同上，合计 54 µA）
------------------------------------------
合计               7050.0 µA  ≈ 6 天
```

**对照结论**：软件部分贡献 54 µA，板级开销贡献 7000 µA。
如果只报"7 mA"，会掩盖软件工作的价值；只报"54 µA"，则是在说谎。
正确做法是两个数字都给，并说明差值来源。

## 4. 采样间隔的影响

| 间隔 | 模型平均电流 | 1000 mAh 续航 | 90 天容量 |
|---:|---:|---:|---|
| 10 s | 88.7 µA | 470 天 | 12.4 MB ❌ |
| 60 s | 54.0 µA | 772 天 | 2.07 MB ✅ |
| 300 s | 48.4 µA | 861 天 | 0.41 MB ✅ |

（数字来自 `tools/power_budget.py`，可直接复现。1 s 档不在考虑范围内：
90 天需要 124 MB，远超 W25Q64 容量。）

10 s 档装不下 90 天数据，这是**存储容量**限制，不是功耗限制。
需要短间隔长周期时应降低记录精度（例如只存温度、去掉 vbat）或换更大 Flash。

## 6. 已知限制

1. **最大睡眠 60 s**。更长的等待应改用 RTC alarm；当前实现限制在 60 s
   是为了让 RTC 读数误差不累积。
2. **1 Hz 唤醒是常开的**。即使没有任务要跑，每秒也会醒一次并恢复 PLL。
   若把 CLKOUT 改成"只在下次任务到期前打开"，还能再降，但复杂度显著上升。
3. **IWDG 未启用**。STOP 模式下 IWDG 继续计数，开启后必须保证每个睡眠块
   短于超时时间的一半，否则会随机复位。
4. **OLED 刷新仍消耗 7.5 µA**。若要进一步降低，可在无按键时完全关闭显示，
   由长按唤醒——但用户看不到温度，产品体验会下降。
