## 1. 项目一句话概括

> **DataLogger** 是一个基于 STM32F103 + FreeRTOS 的工业级本地温度采集与可靠日志系统，实现了从模拟信号采集、实时多任务调度、人机交互到带 CRC 校验的持久化存储的完整数据链，并具备异常复位后的自动数据恢复能力。

**定位关键词**：嵌入式、实时操作系统、数据可靠性、掉电保护、完整闭环

## 2. 核心优势分析

### 2.1 可靠性设计 — 最大亮点

这是本项目区别于"能跑就行"的学生项目的核心差异点。

| 能力 | 实现方式 | 面试价值 |
|------|----------|----------|
| **断电/异常复位恢复** | 每条样本独立 CRC32，启动时逐条扫描恢复有效前缀，自动修复文件元数据 | 展示了你理解 Flash 写入不是原子操作，知道 commit window 问题 |
| **配置双区冗余** | A/B 双区 + 版本号 + CRC，先写 B 验证再写 A，任意时刻断电可恢复 | 展示了工业级配置管理思维 |
| **故障诊断隔离** | 故障钩子只写 volatile 全局变量，不调 UART/队列/互斥锁，避免二次故障掩盖根因 | 展示了真实的 debug 经验和对 FreeRTOS 中断上下文的深入理解 |
| **样本计数语义保证** | `Cnt` 只计数已通过 CRC 验证并成功写入 Flash 的样本，而非传感器读取次数 | 展示了数据完整性的闭环思维 |

**面试时可以这样说**：
> "这个项目最让我自豪的是可靠性设计。我在实板上调试时遇到过一个问题：手动复位后样本计数停在 1 不再增长。根因是复位发生在数据写入后、文件 CRC 提交前——数据本体有效但元数据标记为无效。我实现了逐记录 CRC 扫描恢复机制，让系统在启动时自动识别并修复这种不一致状态。这个经历让我深刻理解了嵌入式存储的一致性模型。"

### 2.2 完整的嵌入式软件架构

不是外设驱动的简单堆砌，而是有明确分层和设计原则的工程：

```text
App 层（任务协作、IPC）
  ↓
Service 层（UI 状态机、日志系统、文件系统、传感器算法、配置管理）
  ↓
BSP 层（SPI Flash、I2C OLED、按键消抖、UART）
  ↓
HAL 层（STM32 HAL + CMSIS）
  ↓
硬件层（STM32F103 + NTC + SSD1306 + W25Q64）
```

**架构亮点**：
- **队列解耦**：DataProd 通过 FreeRTOS 队列（16×80B）异步投递文本日志，Logger 任务异步消费，避免 Flash 写入阻塞传感器采集
- **互斥锁粒度**：Flash 操作由调用链在事务外层持锁，而非每个 SPI 操作单独加锁——保证"校验→写入→更新索引→更新超级块"的原子性
- **UI 快照模式**：Display 通过互斥锁一次性复制 120 字节 UI 状态快照，然后在锁外完成字符串格式化和 I2C 通信——最小化锁持有时间

### 2.3 传感器信号处理链

从模拟电压到物理温度的完整处理链：

```text
16 次过采样 → 去极值平均 → B 参数方程换算 → IIR 低通滤波 → 异常分类
```

- 16 次采样去除最大最小值后取平均——对单次尖峰/跌落有容错，计算量小，适合 Cortex-M3
- 5 种传感器状态分类（OK / SHORT / OPEN / RANGE / ADC），异常数据仍写入样本便于离线分析
- 软件浮点运算在无 FPU 的 Cortex-M3 上完成，展示了性能约束意识

### 2.4 自定义文件系统

在 W25Q64（8MB SPI Flash）上实现的简易文件系统：

- **超级块 + 索引表 + 数据区** 三层结构
- **预留空间分配**：sample 文件首次写入预分配 2MB，避免随数据增长反复迁移
- **页安全写入**：PageSafeWrite 保证单次写入不跨 256 字节页边界
- **分配冲突检测**：ValidateAllocRange 检查新分配区域不覆盖已有文件

> 面试坦白技巧：可以主动说明"这是为了展示对 Flash 存储原理的理解而自行实现的；生产项目中我会优先评估 LittleFS 等成熟方案，它们提供更完整的事务日志和磨损均衡。"

### 2.5 内存约束下的工程决策

STM32F103C8T6 仅 20KB SRAM，最终占用 16440 字节（约 80%）：

| 优化决策 | 效果 |
|----------|------|
| CLI 和 Monitor 任务默认关闭 | 节省 2 个任务栈 + 缓冲区 |
| 固定大小记录（LogRecord_t 80B, SampleRecord_t 24B） | 零堆碎片，无动态分配 |
| OLED 帧缓冲复用（1024B 静态） | 避免 DMA 双缓冲 |
| DataProd 栈从 128→256 words | 解决 snprintf + 浮点库栈溢出，剩余 124 words |

### 2.6 真实的调试与验证

这是简历的加分项——证明你的代码在真实硬件上跑过：

- 使用 **AixProbe**（OpenOCD 上位机）进行寄存器级诊断
- 验证了 RCC/GPIO/FLASH/ADC/I2C1/SPI1 寄存器与配置一致
- 确认 CFSR=0, HFSR=0（无 HardFault）
- 实测样本从 15 增长到 23（5.5 秒），文件从 360 字节增长到 552 字节
- 修复了 3 个真实 bug（栈溢出二次断言、样本计数停止、RAM 链接溢出）

## 4. 面试话术

### 4.1 开场介绍（1-2 分钟）

> "我最近做了一个嵌入式数据采集项目叫 DataLogger。它是一个基于 STM32F103 和 FreeRTOS 的温度记录仪。
>
> 这个项目有两个我认为比较有意思的地方：
>
> 第一是**数据可靠性**。我花了比较多精力处理 Flash 存储的一致性问题。比如系统在写入过程中突然掉电或复位，Flash 里可能有一部分有效数据但文件元数据还没更新。我设计了逐记录的 CRC 校验和启动恢复机制——启动时扫描每条样本，通过记录自己的 CRC 判断是否有效，然后自动修复文件元数据。配置存储用了 A/B 双区加版本号的方式，确保任何时候断电都能恢复到上一次有效配置。
>
> 第二是**系统的工程完整性**。从 NTC 模拟信号采集、16 次过采样去极值、Beta 模型温度换算、低通滤波，到 FreeRTOS 多任务协作——采集任务、日志任务、显示任务各司其职，通过队列和互斥锁通信，再到 OLED 显示和按键交互，最后落到 W25Q64 的持久化存储。这是一条完整的闭环。
>
> 整个项目在 20K SRAM 的约束下跑通，最终构建 0 Error 0 Warning，在实板上用 AixProbe 验证过寄存器状态和 Fault 标志位。"

### 4.2 技术深挖时的回答策略

#### 如果面试官问 "为什么不用现成的文件系统？"

> "有两个原因。一是这个项目的目标之一是深入理解 Flash 存储——页编程限制、扇区擦除、写入非原子性这些特性，自己实现一遍才能真正理解为什么 LittleFS 要做事务日志和磨损均衡。二是系统只需要管理 2-3 个固定文件，引入完整文件系统的开销和复杂度其实超过了收益。
>
> 不过如果这是要量产的产品，我会优先评估 LittleFS——它在掉电保护和磨损均衡方面更成熟。我这边的自定义实现可以看作是对文件系统原理的一次深度实践。"

#### 如果面试官问 "你遇到的最难 bug 是什么？"

> "有一个印象很深的 bug：DataProd 任务栈溢出，但现象完全被掩盖了。OLED 显示异常，AixProbe 暂停时 PC 卡在 FreeRTOS 的断言死循环里。一开始以为是 UART 互斥锁的问题。
>
> 后来发现真正的故障链是：DataProd 栈溢出 → 进入栈溢出钩子 → 旧钩子里调了 UART 发送 → UART 内部尝试获取互斥锁 → 在 PendSV/中断上下文里触发了 FreeRTOS 的临界区断言。第二个断言完全掩盖了最初的栈溢出。
>
> 修复方案是：把 DataProd 栈从 128 words 扩到 256 words，同时把故障钩子改成只写 volatile 全局变量——不调 UART、不拿锁、不用队列。这样即使发生故障也能通过调试器直接读内存定位根因。"

#### 如果面试官问 "队列满了怎么办？"

> "文本日志队列有 16 个槽位，生产者投递时超时 50ms。如果超时意味着 Logger 任务没来得及消费——可能是 Flash 操作比较慢。这时候生产者不会无限阻塞，而是递增 g_log_dropped 计数器并丢弃本条日志。OLED 首页会显示 Drop 计数，用户可以据此判断是否需要降低采样频率。
>
> 结构化样本走的是同步写入路径，因为样本的语义要求'写入成功才计数'——我需要明确知道哪些数据已经安全落盘。"

#### 如果面试官问 "为什么用 FreeRTOS 而不是裸机？"

> "因为系统有三类时间特性完全不同的操作：传感器采样是周期性的（100ms-5s），日志写入是异步的（不能阻塞采集），OLED 刷新和按键响应要求低延迟（50ms 扫描周期）。如果用裸机主循环，要么超级循环变得非常复杂，要么某些操作的实时性无法保证。
>
> FreeRTOS 的抢占式调度天然匹配这个场景。三个任务各司其职：DataProd 按配置周期 vTaskDelay，Logger 阻塞在队列等待上不占 CPU，Display 每 50ms 扫描按键和刷新屏幕。优先级设置上 Logger 最高——目的是尽快从队列取走日志，降低队列满的概率。"

### 4.3 展示思考深度的话术

如果面试官让你自由发挥，可以从这几个角度延展：

**关于权衡：**
> "这个项目里我做了很多权衡。比如样本同步写 vs 文本日志异步写——样本的计数语义要求'确认落盘才计数'，所以走同步路径；文本日志允许偶尔丢弃，所以用队列解耦。再比如为什么不加蓝牙或云平台——我觉得先保证'单机采集到存储'这条链路的可靠性，比横向堆功能更有价值。"

**关于已知不足（展示技术诚实度）：**
> "这个项目有几个我清楚知道需要改进的地方：文件系统元数据的提交还不是完整的事务日志，当前靠逐条 CRC 恢复来处理已知的断电窗口；文本日志还没有样本那样的逐条恢复；文件索引更新比较频繁，可以通过批量提交来减少 Flash 擦写次数。这些都在技术文档里记录为后续演进方向。"

## 5. 常见追问与回答

### Q1: 为什么选 STM32F103C8T6？

> F103 是最经典的 Cortex-M3 芯片，资源适中（20KB SRAM / 64KB Flash），外设齐全，适合这类中等复杂度的数据采集项目。C8T6 的资源约束本身就是一个很好的设计练习——你需要认真管理每一块内存。

### Q2: CRC32 为什么用 IEEE 802.3 而不是其他？

> 802.3 CRC32 是嵌入式最常用的，查表实现效率高，检测能力对这类应用足够。多项式是反射的 0xEDB88320，初值和结果都异或 0xFFFFFFFF。关键是每处 CRC 覆盖的范围要明确定义——样本记录的 CRC 只覆盖前 20 字节，不包含 CRC 字段本身。

### Q3: 怎么保证 OLED 刷新不影响按键响应？

> Display 任务主循环是 50ms——每轮都扫描按键。但 OLED 常规刷新周期是 1000ms。按键事件触发时会立即刷新 OLED，所以用户按键后不需要等 1 秒才看到反馈。这是一种事件驱动的刷新调度。

### Q4: 如果 NTC 传感器坏了怎么办？

> 系统有 5 种传感器状态分类。SHORT（ADC<20，AO 接近 0V）、OPEN（ADC>4075，AO 接近 3.3V）、RANGE（换算温度超出 -20~125°C）、ADC（HAL 操作失败）。异常数据仍然会写入 sample 文件，只是 ntc_status 标记为异常状态——这样离线分析时可以知道故障发生的准确时间。

### Q5: 最大能存多少条数据？

> 2MB 预留区，每条 24 字节，约 87000 条。1 秒周期跑约 24 小时，5 秒周期跑约 5 天。写满后当前版本返回空间不足，不会覆盖旧数据。环形覆盖是后续演进方向。

### Q6: 项目代码量多大？构建结果？

> 约 36,500 行代码（不含 HAL 库），构建结果：ROM 39,488 字节，RAM 16,440 字节（含 FreeRTOS heap 7KB + OLED 帧缓冲 1KB + 索引缓存 1KB + 队列数据 1.3KB + 3 个任务栈各 1KB），0 Error 0 Warning。
